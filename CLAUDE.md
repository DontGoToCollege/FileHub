# FileHub: notes for Claude

Build, test and release recipes, decisions and gotchas, kept in the repo so every computer has them.

FileHub lives at `%USERPROFILE%\Music\Claude\Projects\FileHub` (solution root; project `src\FileHub`). Started 2026-09-15 as a "shell" the user will test and give feedback on.

- Target `net8.0-windows`, WPF + WinForms (tray icon only; WinForms/Drawing implicit usings are removed in the csproj to avoid type ambiguity).
- Publish with `.\publish.ps1` → `dist\FileHub.exe` (self-contained single file, ~68 MB, ReadyToRun). Machine has SDK 10 with the 8.0 runtime pack cached.
- Data in `FileHub-Data\` next to the exe (since 0.3.8; here the project root, git-ignored): settings.json, index.fhdb snapshot, meta.db SQLite with FTS5, logs\. Older versions used `%LocalAppData%\FileHub`, moved over on first start. Since 0.3.9 Settings can move it anywhere (`FileHub-Data.location` next to the exe records it; the move runs at the next start via `FileHub-Data.move`; `--move-data <folder>` does the same). Claude's tools see a stale sandboxed copy of `%LocalAppData%` (Claude package `LocalCache\Local`), not the real folder. Run a debug build against real data with env `FILEHUB_DATA=<dir>` (else it makes `bin\...\FileHub-Data`).
- Index of this machine: ~618k entries, full crawl ≈23 s, snapshot load ≈0.3 s.
- Default hub hotkey Ctrl+Alt+Space fails to register on this machine (taken by another app); user can change it in Settings.
- Smoke-test technique that works: launch exe, then capture windows with `PrintWindow(hwnd, hdc, 2)` via PowerShell Add-Type (CopyFromScreen gives garbage for the WPF window). Close it with `FileHub.exe --exit` before republishing and restart it with `--tray` (a launch with no arguments opens an Explorer window in front, taking the owner's focus) (graceful: since 0.3.1 it saves the index on exit; plain `taskkill` without /F does nothing to it, /F loses unsaved live changes).

- **Background testing (no focus, owner keeps working) — use this first.** `FileHub.exe --exit`, then start the build with `--test --tray` (WMI `Win32_Process` Create). In test mode every window opens off-screen (x ≈ -32768), never topmost and with `WS_EX_NOACTIVATE`, and the Start menu stays open unfocused. Drive it with second launches: `FileHub.exe --start` / `<folder>` / `--hub <query>`; fill text boxes with `FileHub.exe --set-text [TitlePart:]BoxName "text"` (x:Name, newest window first); `--menu-sources <file>` logs which program each right-click entry comes from (the menu editor's From column) — never UI Automation `ValuePattern.SetValue`, which focuses the box and pulls the window to the front. Never open a drop-down or other popup (UIA `ExpandCollapsePattern.Expand`): WPF focuses its window on open and the popup lands on the visible screen. A 10 ms foreground probe on 2026-11-22 showed every other test-mode step (Hub `--page`, `--start`, `--set-text`, Explorer, `--exit`) leaves the foreground alone. Read layout with UI Automation (BoundingRectangle, `TextPattern` ranges), capture with `PrintWindow(hwnd, hdc, 2)` from a per-monitor-DPI-aware process, and check the foreground window is unchanged after each step. Finish with `--exit` and restart the release exe. Only real-input things (drag-select, the physical Win key, hover tooltips) still need the owner to step away.
- Versioning now follows the global CLAUDE.md setup (since 2026-10-27): bump `<Version>` in the csproj (+ app.manifest where present) and add a CHANGELOG entry, then `.\publish.ps1`, which refuses an already-archived version and keeps `<Exe>.exe` at the project root plus `Versions\Archive\<Exe>-<version>.exe`; commit, push, and `gh release create v<version> <Exe>.exe`. `archive-version.ps1` is gone (git holds the source history; old snapshot folders sit in `Versions\Archive`).
- User wants minimal, targeted changes per iteration; preserve existing design/behavior.
- **Speed is the point of FileHub.** Searches, sorting, filter tabs, thumbnails and content searches must feel instant: aim for well under 100 ms, and treat anything over ~300 ms as a bug to fix, not a number to report.
- **Keep timing tests and other checks short (owner's rule, 2026-11-23).** Use a small sample (a handful of queries, a copy of one table or a few thousand rows, never the whole 5 GB `meta.db`), and keep each command to well under a minute. Stop as soon as one sample answers the question. Never sit on a long wait (a full rebuild, a migration, a big copy or experiment) in the foreground: run it in the background and keep working or reporting, or ask first. On 2026-11-23 an 18-minute stretch with no visible progress (a 5-minute FTS experiment on a full DB copy plus a 5-minute migration wait) is what prompted this.
- **Indexing status is the same on every screen (owner's rule, 2026-11-23).** Every background pass (name index, file contents, thumbnails, and any added later) must show on Explorer's status line, the Hub's side panel and Hub → Index & database, all through `UI\Common\IndexingStatus.cs`: never wire a screen to one pass's StatusChanged directly. The Start menu shows none. A new pass gets its line in `IndexingStatus.Passes` and its event in `Subscribe`/`Unsubscribe`, and its status texts name the pass ("Thumbnails idle", not "Idle").
- User runs StartIsBack; Claude desktop owns Ctrl+Alt+Space (FileHub's LL keyboard hook now captures it first).
- `Slow folder load` lines in the log (>400 ms) identify slow Explorer navigations.
- **Slow, stuck or "doing nothing" reports: logs, then dotnet-stack, before reading code (owner's rule, 2026-11-24).** First read the day's `FileHub-Data\logs\filehub-<yyyymmdd>.log` (grep it, don't print it whole). Then sample the running app's threads with `~/.dotnet/tools/dotnet-stack.exe report -p <pid>` (a `dependencies.json` tool, installed by rules-band; works on the self-contained release exe, takes no focus, changes nothing). Take 10-15 samples and count which `FileHub!` frames the thread in question sits in (`awk 'BEGIN{RS="Thread [(]"} /ContentIndexer.Loop/'` isolates one thread): that shows where the time really goes. Each report takes a few seconds, so run a long sample loop in the background. On 2026-11-24 this showed the content pass spending most of its time reading changed files one at a time, not in its 500-file batches.
- Never open the live `meta.db` read-write from a script while FileHub runs (a Bash-tool read on 2026-11-22 likely corrupted it; the Claude app's view of `%LocalAppData%` is a stale sandboxed copy). Inspect a copy, or use `?mode=ro&immutable=1`. Since 0.3.0 the FTS rowid equals the `content_meta`/`props` rowid (`PRAGMA user_version` 1).

**Why:** the user wants feedback-driven iteration on this app; knowing the layout and the validation recipe avoids re-deriving it.
**How to apply:** for follow-up requests, edit under `src\FileHub`, rebuild with `dotnet build`, republish with publish.ps1, smoke-test with PrintWindow captures. See user-testing-preference.
